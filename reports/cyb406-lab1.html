CYB406 — Lab 1

Secure Investigative Environment (Tor Sandbox)

Rukayya Nasidi Miva Open University July 16, 2026

Built an isolated VirtualBox/Ubuntu sandbox with clipboard, drag-and-drop, and shared folders disabled, then hardened Tor Browser to its "Safest" security level. Verified there was no identity leakage by comparing DNS resolution, exit-node IP, and geolocation across Tor vs. regular browsing.

Tor VirtualBox DNS Leak Testing OPSEC

1. Configuration Documentation

This lab establishes an isolated "sandbox" environment to safely access anonymized and hidden networks without exposing the host machine to risk. A Type-2 hypervisor (Oracle VirtualBox) was used to host a Ubuntu 24.04.4 LTS guest operating system.

The virtual machine was built using Oracle VirtualBox as the Type-2 hypervisor, hosting Ubuntu 24.04.4 LTS as the guest operating system. Storage was migrated from the installation ISO (mounted on the IDE controller) to a dedicated virtual hard disk (.vdi) on a SATA controller, confirming the OS installation was self-contained and independent of any physical or virtual optical media.

To isolate the guest from the host and prevent malware or data from crossing between environments, the following settings were required under VM Settings → General → Advanced:

  • Shared Clipboard: Disabled
  • Drag'n'Drop: Disabled
  • Shared Folders: none configured

A clean snapshot ("Clean install — pre-TOR") was also taken after the base OS installation, allowing the environment to be reverted to a known-safe state after any risky browsing session, in line with the snapshot management practice required for Week 8.

2. Connectivity Verification

The TOR Browser (version 15.0.18, Linux x86_64) was downloaded directly from the official Tor Project website and launched inside the isolated Ubuntu guest. The browser successfully established a circuit into the Tor network and confirmed a working connection with the default landing page reporting that the browser was correctly configured to use Tor.

Security was then raised to the "Safest" level in Tor Browser's Advanced Security Settings. This setting automatically disables JavaScript on all sites, HTML5 media auto-play, and several other high-risk browser features — functionally equivalent to running NoScript in its most restrictive mode.

A verified .onion v3 address (56-character format, ending in .onion) was then compared against its equivalent Clear Net (regular HTTPS) address:

Attribute.onion (v3, via Tor)Clear Net (HTTPS)
Address structure56-character random string + .onionHuman-readable domain name (e.g. nytimes.com)
Load timeNoticeably slower (multiple relay hops)Fast, direct connection
ReadabilityNot human-readable / not memorableEasy to read and remember

As expected, the .onion service was slower to load and used an unreadable, randomly-generated address, while the Clear Net version loaded quickly with a conventional, memorable domain name. This trade-off is the direct cost of the extra relay hops and encryption layers that give Tor its anonymity properties.

3. Vulnerability Assessment

A DNS leak test (dnsleaktest.com, Extended Test) was run in two conditions to evaluate whether the guest machine's real network identity was exposed:

ConditionPublic IPDNS Resolver / ISPGeolocation
Via Tor Browser185.220.101.129 (known Tor exit relay)Cloudflare, Gigahost, MOJI, WoodyNetParis, France / Sandefjord, Norway
Regular (non-Tor) browser98.97.77.173Google Public DNSJohannesburg, South Africa

Analysis: No DNS leak was detected while using Tor Browser — none of the resolving servers were tied to the real ISP or the user's actual location (Lagos, Nigeria); instead, resolution occurred through Tor relay infrastructure in Europe. The non-Tor baseline test revealed a different but still non-local resolution path through Google's public DNS, geolocated to South Africa rather than the user's real city. This illustrates an important nuance: even without a literal ISP match, an unprotected browser still reveals a consistent, traceable DNS path that an observer on the same network (e.g. an ISP or local network administrator) could correlate with browsing activity. This is the core risk of a DNS leak — even when the content of traffic is encrypted (as with HTTPS or Tor's onion routing), a leaked DNS query still reveals which domains a user is visiting, undermining the anonymity that Tor is meant to provide.

Secondary finding: setting Tor Browser's security level to "Safest" disables JavaScript, which caused the DNS leak test page to hang indefinitely, since the site's results depend on client-side scripting to render. Security had to be temporarily lowered to "Standard" to complete the test, then restored to "Safest" afterward — a practical example of the security-versus-usability trade-off referenced throughout this course: the strongest privacy configuration can also break legitimate tooling, requiring deliberate, temporary, and documented exceptions rather than leaving the browser permanently in a weaker state.
