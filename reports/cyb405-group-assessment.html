CYB405 — Group Lab Assessment

Full-Spectrum Ethical Hacking: 8 Labs on Kali Linux

10-person group assessment Miva Open University Labs 1–8

A group assessment run entirely inside an isolated VMware lab (Kali, Metasploitable2, Windows Server), progressing from environment setup through recon, enumeration, exploitation, malware reverse engineering, web app hacking, mobile/wireless security, and IDS evasion. Screenshots below are drawn from the shared team submission; anything identifying individual teammates has been left out.

Lab 1 — Virtual Lab Setup & Configuration

Objective: establish a secure, functional, and fully isolated hacking environment for all subsequent labs.

Kali Linux, Metasploitable2, and Windows Server 2019 were installed in VMware and wired into a Host-Only network (VMnet1, 192.168.56.0/24) to keep the lab fully isolated from the external internet. DHCP was configured to issue addresses starting from 192.168.56.101, giving each VM a predictable, static-like lease.

Connectivity testing surfaced a real troubleshooting case: pings from Kali to Metasploitable2 worked immediately, but Kali to Windows Server 2019 failed because the default Windows Defender Firewall blocks ICMP Echo Requests. The fix was a new inbound firewall rule on the Windows Server VM: 

netsh advfirewall firewall add rule name="Allow ICMP Ping" dir=in action=allow protocol=icmpv4:8,any

A baseline Nmap scan (nmap -sS -p- -T4 -oA baseline_scan 192.168.56.0/24) established the starting port/service picture for the whole subnet, and the entire setup — connectivity checks, a filtered tshark capture, the baseline scan, and .xml/.pcap reporting — was wrapped into a single Bash automation script (environment_setup.sh) so the environment could be rebuilt reproducibly.

Lab 2 — Footprinting & Reconnaissance

Objective: gather as much information as possible about target systems using passive and active methods.

The network mode was switched to NAT for the passive phase to allow public-DNS lookups without exposing the internal lab. whois pulled domain registration data (registrar, name servers, creation/update dates) for a public test domain, and dig added A, MX, NS, and TXT record detail — including an SPF record showing the domain rejects mail entirely.

Switching back to Host-Only, an aggressive Nmap scan (nmap -sS -sV -O -p1-65535 -T4) against Metasploitable2 found 30 open ports and fingerprinted the OS as Linux 2.6.9–2.6.33. A Nikto scan of the same host's web service flagged an outdated Apache/2.2.8 build, an enabled HTTP TRACE method (XST-vulnerable), and exposed directories such as /phpMyAdmin/. Finally, an Nmap XML scan was transformed into a browsable HTML report with xsltproc for a human-readable topology view.

Lab 3 — Network Scanning & Enumeration

Objective: move from open-port discovery to detailed service enumeration, SMB/RPC mapping, and a full vulnerability assessment.

A Masscan sweep of the subnet illustrated a real speed/reliability trade-off: a conservative 1,000 packets/sec run projected over 3 hours to complete, while pushing to 500,000 packets/sec finished fast but returned almost nothing — the virtualized Host-Only interface likely couldn't keep up with, or filtered, the high-rate injection. Nmap's SMB enumeration scripts and rpcinfo filled the gap instead, revealing an outdated Samba 3.0.20-Debian install with a share literally commented "oh noes!" that allowed anonymous login, and enum4linux -a confirmed the WORKGROUP name and several default usernames (administrator, guest, root).

A full Nessus Essentials "Basic Network Scan" against the subnet closed the lab out with hard numbers: 5 critical vulnerabilities, 3 high, and 126 total findings on the Metasploitable2 host alone — all raw outputs converted to HTML via xsltproc for the final portfolio.

Lab 4 — System Hacking & Privilege Escalation

Objective: move from enumeration to active exploitation, gain a shell, and document remediation.

Using the vsftpd 2.3.4 version identified in Lab 3, searchsploit turned up a known backdoor exploit (CVE-2011-2523). Metasploit's exploit/unix/ftp/vsftpd_234_backdoor module fired it against the target, spawning a Meterpreter session that dropped straight into a root shell — no privilege escalation needed, since the backdoor itself grants uid=0. A stable interactive shell was then established with the classic python -c 'import pty; pty.spawn("/bin/bash")' trick.

From there, evidence gathering pulled /etc/passwd (full user list) and /etc/shadow (password hashes), and sudo -l confirmed unrestricted root sudo access. The remediation plan that followed: upgrade vsftpd past 3.0.5, move password hashing off MD5 to SHA-256/512, apply regular kernel/security patching, block legacy ports like FTP (21) and Telnet (23), rotate default credentials, and set a default-deny firewall policy.

Lab 5 — Malware Analysis & Reverse Engineering

Objective: statically and dynamically analyze a malicious binary, identify IOCs, and write a detection rule.

A sample ELF 64-bit binary was hashed (MD5/SHA256) and inspected with strings and readelf, which showed it had been packed with UPX and stripped of section headers — both classic anti-analysis techniques. Loaded into Ghidra, the decompiler mapped the entry point and rendered the disassembly as readable C-like pseudocode, exposing internal function calls and the binary's branching logic.

Dynamic analysis with strace caught the binary reading /etc/passwd (credential harvesting) and performing self-deletion (MITRE T1070.004). A live network capture showed it calling out to a remote IP over QUIC on port 443 — an encrypted channel choice (MITRE T1573) specifically suited to slipping past deep packet inspection. Cross-referencing the SHA256 hash on VirusTotal got 39/65 vendor detections, positively identifying it as part of the Merlin trojan family (a C2 / post-exploitation framework). The lab closed with a custom YARA rule built from these IOCs, validated against the original sample.

Lab 6 — Web Application Hacking (SQL Injection & XSS)

Objective: identify and exploit SQL injection and XSS in a deliberately vulnerable web app (OWASP Juice Shop), then recommend mitigations.

Gobuster mapped the attack surface first, turning up /login, /search, and /admin endpoints. A manual login-bypass injection — username=admin' OR '1'='1&password=foo — worked immediately, confirming missing input sanitisation and no prepared statements. sqlmap then automated the exploitation, dumping usernames, emails, and password hashes straight out of the users table.

XSS testing found both stored and reflected variants: a <script>alert('XSS')</script> payload executed unsanitised in the browser via search/feedback fields, confirming risk of session hijacking, cookie theft, and page defacement. Burp Suite was used to intercept and tamper with requests directly, confirming parameters weren't validated server-side either. Recommendations: parameterised queries and input validation for the injection side; output encoding, a Content Security Policy, and input sanitisation for XSS; plus the general basics — HTTPS, a WAF, and regular security testing.

Lab 7 — Wireless & Mobile Security

Objective: assess Wi-Fi network security and perform static/dynamic analysis on an Android APK.

The wireless half of this lab hit a hardware wall: starting monitor mode with airmon-ng failed because no compatible wireless adapter existed inside the virtualized VMware environment — only loopback, Ethernet, and Docker interfaces were available, confirmed with ip link show. WPA2 handshake capture and cracking simply weren't possible without physical USB Wi-Fi hardware passed through to the VM, and that limitation was documented rather than worked around.

The mobile half was more fruitful. DIVA (Damn Insecure and Vulnerable App) was decompiled with apktool, and a recursive grep for "password", "api_key", and "secret" across the extracted resources turned up multiple layout XML files clearly built to collect credentials. Loading the APK into JADX-GUI for source review confirmed the worst case: an APICreds2Activity class with hardcoded plaintext credentials and an API key sitting directly in the Java source. Fixes recommended: never store secrets in plaintext source, use the Android Keystore or SQLCipher for local sensitive data, and apply ProGuard/R8 obfuscation to raise the bar for reverse engineering.

Lab 8 — Evasion, IDS/Firewall Bypass & DDoS Simulation

Objective: evaluate IDS evasion techniques, detect honeypot behaviour, and run a controlled, low-impact DoS simulation.

Several Nmap evasion techniques were tested against Metasploitable2: MTU fragmentation (an initial --mtu 24 run showed no real fragmentation in Wireshark, but dropping to --mtu 16 produced genuinely fragmented IP packets), a decoy scan (-D RND:10) mixing 10 random spoofed IPs with the real attacker address, and data-length padding (--data-length 100) to inflate SYN packets past simple signature filters. A hand-crafted Scapy fragmentation script split a 2 KB ICMP payload into 2 IP fragments and confirmed the reassembled length in Wireshark byte-for-byte.

Honeypot detection used NULL, FIN, and Xmas scans — all three violate the TCP spec in ways real honeypots often mishandle. The target returned 2,933 RST|ACK packets with a consistent TTL of 64, exactly what a genuine Linux TCP/IP stack does and what most low-interaction honeypots fail to replicate — concluding the target was a real host, not a honeypot. Banner grabbing against FTP, SSH, and HTTP confirmed legitimate, consistent service banners as a second line of evidence.

For the DoS phase, running baseline/attack/recovery measurement across four terminals manually was impractical, so the whole workflow was scripted (slowloris_auto.sh): 200 connections held open for 60 seconds, HTTP/SSH/FTP availability polled throughout, then 6 recovery measurements over the following 30 seconds. Response time jumped from roughly 0.012s at baseline to 49.93s under attack, then returned to baseline within the recovery window — demonstrating both the impact of a slow-connection DoS and the target's ability to recover cleanly once it stopped.
