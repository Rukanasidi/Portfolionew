CYB402 — Week 1

Steganography: Access Methods & Data Hiding

Rukayya Nasidi Miva Open University Exercises 1–9

Hid and recovered data in image and audio carriers using Steghide (LSB substitution), then tested steganalysis methods to detect it. Examined how the same technique is abused for malware C2 and exfiltration, and the legal implications of deliberate concealment.

Exercise 1 — Installing a DHCPv6 Server

Objective: install a DHCPv6 server on a Linux-based system.

Updated and upgraded the system package list, installed the ISC DHCP server package (isc-dhcp-server), which provides both IPv4 and IPv6 support, and verified the installation and service state with systemctl status isc-dhcp-server.

The installation completed without errors, and systemctl automatically created service symlinks for both isc-dhcp-server.service and isc-dhcp-server6.service, confirming IPv6 support was installed alongside IPv4. Checking the service status immediately after installation showed a failed state with the message "not configured to listen on any interfaces" — this is expected behaviour for a fresh install: the DHCP daemon refuses to start until an administrator explicitly configures which network interface and address range it should manage. This distinction — between a failed installation and a service that is installed correctly but simply not yet configured — is an important troubleshooting skill in itself.

Exercise 2 — Practical Steganography Tools

Objective: practice using a steganography tool to hide and extract data from a file.

Selected Steghide as the tool, installed via apt install steghide. Used a JPEG cover image (Ubuntu's built-in wallpaper set) since Steghide requires a JPEG, BMP, WAV, or AU carrier file. Created a short text file containing a secret message, embedded it with steghide embed -cf cover.jpg -ef secret.txt (protected with a passphrase), then extracted it back out with steghide extract -sf cover.jpg and confirmed the recovered text matched the original exactly.

Steghide proved straightforward once the correct file type (JPEG rather than PNG) was selected as the cover file. The command syntax is minimal, and the tool gives clear, unambiguous confirmation messages at each stage. The visual appearance of the cover image was unchanged to the naked eye after embedding — the core use of steganography. The main limitation encountered was Steghide's narrow format support: it will not work with PNG cover files, a common beginner mistake since PNG is Ubuntu's default wallpaper format.

Exercise 3 — Detecting Hidden Data in Files

Objective: explore methods for detecting hidden data using statistical and file signature analysis.

The intended primary tool, StegExpose (a Java-based steganalysis tool), could not be made to produce usable output despite a valid installation, a valid JAR file, and correctly formatted input. This is a known limitation: it has not been actively maintained since around 2015 and has compatibility issues with modern Java runtimes, confirmed by testing multiple invocation syntaxes without success. Rather than a dead end, this was treated as a genuine finding: security analysts frequently encounter unmaintained or poorly documented tooling, and identifying that a tool is unreliable — rather than assuming a hidden message is therefore absent — is itself part of the analysis process.

As an alternative, a direct file-size comparison between the original cover image (1,957,897 bytes) and the same image after Steghide embedding (2,243,324 bytes) showed a difference of roughly 285 KB — a substantial and easily detectable change for a single short sentence of hidden text, demonstrating that simple LSB embedding tools are not always size-neutral. Metadata inspection with exiftool did not reveal any field that explicitly indicated hidden content, which is expected, but it did provide a clean baseline of the image's standard JPEG properties for comparison.

Summary of challenges: outdated/unmaintained detection tooling produced no output despite correct usage, illustrating that tool reliability is itself a practical constraint in steganalysis. Detecting steganography purely by visual inspection is not feasible — quantitative methods (file size, metadata) are required. And a lack of hidden-data indicators in metadata does not itself prove a file is clean, since steganography is designed to avoid such traces.

Exercise 4 — Steganography and Malware Communication

Objective: explore the use of steganography in malware communication and data exfiltration.

Created a harmless text file labelled as a simulated payload, standing in for malicious content for lab purposes only, embedded it into a cover image using Steghide (representing how an attacker might conceal exfiltrated data or command instructions inside an image file), then extracted and read it back to simulate the attacker-side retrieval step.

Most network security controls — firewalls, antivirus, intrusion detection systems — are built to inspect traffic for known malicious signatures or suspicious file types such as executables and scripts. An image file transmitted over an ordinary web request does not trigger these controls, because a JPEG is treated as benign content by default. By embedding stolen data or attacker instructions inside such a file, an attacker can move information across a monitored boundary while appearing to do nothing more than share a photo.

From a legal and ethical standpoint, using steganography to conceal data theft, malware communication, or the transfer of illegal content does not reduce culpability — courts generally treat deliberate concealment as an aggravating factor rather than a mitigating one, since it demonstrates clear intent to evade detection. The technology itself is ethically neutral; it is also used legitimately for digital watermarking, copyright protection, and secure communication for journalists or activists. It is the intent and context of use that determines whether a given application is ethical or unlawful.

Exercise 5 — Ethical and Legal Issues in Steganography

Objective: examine the ethical concerns and legal ramifications of using steganography for illicit purposes.

Steganography sits on a spectrum of legitimate and illegitimate use cases. Legitimate applications include digital watermarking for copyright protection, secure and deniable communication for individuals in high-risk environments (such as journalists or human rights workers operating under surveillance), and general privacy-preserving communication. Illegitimate applications include concealment of malware command-and-control traffic, exfiltration of stolen data, and distribution of illegal content disguised as innocuous files. Because the technique itself carries no inherent malicious signature, ethical evaluation must focus on the intent behind its use and the nature of the content being concealed, rather than the technique itself.

Where steganography is used to facilitate an underlying crime, the concealment itself does not create a separate legal shield. In most jurisdictions, deliberately hiding evidence of a crime is treated as an aggravating factor, potentially supporting additional charges such as obstruction or intentional concealment, on top of whatever charges apply to the underlying offence. Organisations that fail to account for steganographic exfiltration risk in their security controls may also face regulatory consequences under data protection law if a breach occurs through this channel and is later found to have been reasonably foreseeable.

Exercise 6 — Advanced Detection of Steganography

Objective: explore advanced techniques for detecting steganography in digital files.

Re-attempted automated steganalysis with StegExpose (unsuccessful again), repeated the file-size comparison, and extracted and visually compared the least-significant-bit (LSB) plane of a stego image and a clean image using ImageMagick, reducing each to 1-bit depth to expose the low-order bit patterns where LSB steganography embeds data.

A more reliable steganalysis workflow would combine multiple independent signals rather than relying on any single method: automated statistical tests (once run on properly maintained tooling), file size and metadata comparison against a known-clean baseline, and visual/LSB-plane inspection for a final human-reviewed check. Because no single technique proved conclusive on its own, layering methods — and cross-referencing results — produced a far stronger case for the presence of hidden data than any individual test.

Exercise 7 — Countermeasures and Mitigation in Steganography

Objective: understand and apply countermeasures to improve steganography effectiveness.

Encrypted a message using GPG with AES-256 symmetric encryption before embedding, producing an encrypted .gpg file; embedded the encrypted file (rather than the plaintext) into a cover image using Steghide; then extracted the hidden file from the image and successfully decrypted it with GPG, confirming both layers functioned correctly together.

Combining encryption with steganography creates a defence-in-depth effect: even if an attacker or analyst successfully detects and extracts the hidden file (defeating the steganographic layer), they are still left with an AES-256 encrypted blob that is computationally infeasible to read without the correct passphrase. In this lab, the extraction step succeeded exactly as expected, but the recovered file remained unreadable until decrypted separately with GPG, demonstrating that the two layers are independent: compromising one does not compromise the other.

Adaptive algorithms: beyond encryption, adaptive steganography algorithms adjust how and where data is embedded based on the specific characteristics of the cover file — for example, favouring high-texture or high-noise regions of an image where small pixel changes are statistically less anomalous, rather than embedding uniformly across the whole file. This makes the resulting stego file more resistant to statistical detection methods, because the embedded data blends more closely with the image's natural noise profile. The trade-off is added complexity compared to straightforward LSB tools such as Steghide.

Exercise 8 — Steganography and Cybercrime

Objective: analyse how steganography can be misused in cybercrime and how to mitigate these risks.

Based on the technique demonstrated in Exercise 7, a plausible cybercrime scenario involves two parties communicating covertly: one party encrypts a message and embeds it inside an ordinary-looking image, then uploads that image to a public platform such as a forum, social media site, or cloud storage service. The second party downloads the image and extracts the hidden, still-encrypted data. Because the transmitted file is a common image format and does not match any known malware signature, standard network security tooling has no basis to flag the transfer, allowing the communication to proceed undetected.

Recommended countermeasures:

  • Deploy content-aware inspection at network egress points that screens for statistical anomalies in transmitted images, rather than filtering purely by file type or known signatures.
  • Restrict or closely monitor uploads to personal cloud storage and unfamiliar image-hosting services from corporate networks.
  • Apply re-compression of outbound images at the network boundary; because LSB-based steganography is highly sensitive to recompression, this can passively destroy hidden payloads as a side effect of standard image processing.
  • Maintain staff awareness training, since most real-world exfiltration incidents still require an insider action or a successful phishing compromise to move the file out in the first place.

Exercise 9 — Steganography and Compression

Objective: explore the limitations of steganography related to file compression and modification.

Took the stego image from Exercise 2 and converted it from JPEG to PNG, then back to JPEG, to simulate the recompression that commonly occurs when an image is re-saved, reformatted, or uploaded to a third-party platform, then attempted to extract the hidden message using the correct passphrase.

The extraction attempt failed outright, with Steghide reporting that no data could be extracted even with the correct passphrase. This confirms a fundamental limitation of least-significant-bit steganography: the technique depends on the exact preservation of specific pixel byte values, and any process that rewrites those bytes — including format conversion, recompression, or resizing — destroys the embedded data, regardless of whether the recipient has the correct extraction passphrase. In practice, this means LSB-based tools such as Steghide are poorly suited to scenarios where the carrier file is likely to be re-processed, such as images uploaded to social media platforms. This is also directly relevant to the countermeasures in Exercise 8: deliberately recompressing images at a network boundary is a practical, low-cost way to neutralise this class of hidden-data transfer without needing to first detect that hidden data is present.
