Exercise 1 — Understanding Data Hiding and Steganography

Objective: understand the concept of data hiding and its role in cybersecurity, and demonstrate it with a simple practical example.

Copied a JPEG background image as a cover file, embedded a short text message with steghide embed (passphrase protected), and opened the resulting image to visually confirm no detectable change.

Data hiding is the practice of concealing the existence of information, not just its content — this distinguishes it from encryption, which scrambles content but does not disguise the fact that a protected message exists. In a cybersecurity context, this matters because it protects confidentiality even under active monitoring: a network observer sees only an ordinary-looking image file, with nothing to indicate that a message is present at all, let alone what it contains.

Exercise 2 — Encryption vs Data Hiding

Objective: compare encryption and data hiding hands-on, understanding their differences and use cases.

Encrypted a message with GPG (AES-256 symmetric), displayed the encrypted file's raw contents to observe what encrypted output looks like, and separately hid a different message inside a JPEG cover image using Steghide.

The encrypted file appeared as an unreadable block of binary/symbolic characters — visibly and unmistakably scrambled. The steganographic image, by contrast, displayed as a completely ordinary desert landscape photograph with no visible indication that any data was hidden inside it.

Purpose: encryption protects the confidentiality of a message's content, assuming an observer already knows a protected message exists. Data hiding protects the existence of the message itself, so an observer may not even realise there is anything to investigate. Detectability: an encrypted file is trivially identifiable as "something protected" purely from its appearance (high entropy, non-readable structure), even without breaking the encryption. A steganographic file is designed to be statistically and visually indistinguishable from an unmodified original, making detection significantly harder without specialised steganalysis. In practice, the two techniques are complementary rather than competing: encrypting a message before hiding it means that even successful detection and extraction of the hidden data does not immediately expose its content.

Exercise 3 — Watermarking for Copyright Protection

Objective: explore digital watermarking techniques for protecting intellectual property, both visible and invisible.

Created a visible, semi-transparent text watermark ("© Ruqayya CYB402") on a cover image using ImageMagick's convert utility, and separately embedded an invisible watermark — a short copyright/ownership text string — into a different copy of the same image using Steghide, then extracted it back out to verify it could be recovered on demand.

The visible watermark rendered correctly as small, semi-transparent identifying text in the bottom-right corner — noticeable but not obtrusive. The invisible watermark embedded and extracted successfully, with the recovered text matching exactly: "Copyright: Ruqayya, CYB402, 2026".

Visible watermarking is the simpler, lower-effort approach and immediately signals ownership, but it permanently alters the image's appearance and can be cropped or edited out relatively easily. Invisible watermarking preserves the original image completely, and ownership can be proven on demand — but a casual viewer has no visible indication the image is protected at all, and the watermark can be destroyed if the image is later recompressed or reformatted. Visible watermarks deter casual reuse, while invisible watermarks support forensic proof of ownership after the fact, provided the file has not been re-processed.

Exercise 4 — Techniques for Image Steganography (LSB Substitution)

Objective: apply LSB substitution for image steganography and confirm the cover image remains visually unchanged.

Converted a PNG background image to JPEG (Steghide's required format), embedded a descriptive text message, extracted it back out and confirmed it matched exactly, then visually inspected the final stego image for any detectable change.

Steghide alters the least-significant bit of pixel colour values in the cover image to encode the hidden message's binary data — a change small enough to be imperceptible to the human eye but large enough, cumulatively, to be recoverable with the correct extraction key. Its main limitation, established elsewhere in this module, is that the technique is entirely dependent on the exact byte values of the carrier file and does not survive recompression or reformatting.

Exercise 5 — Audio Steganography

Objective: practice hiding data within an audio file.

Copied a system WAV sound file (Ubuntu's built-in ALSA sound set) to use as the audio carrier, embedded a text message with steghide embed, extracted it back out and confirmed it matched exactly, then played the resulting audio with aplay to confirm it remained a valid, playable WAV file after embedding.

Audio steganography applies the same underlying principle as image steganography — encoding hidden data into the least significant, perceptually insignificant details of the carrier — but operates on audio sample values rather than pixel colour values. Steghide was used here rather than a Windows-only tool such as DeepSound, since the lab environment is Linux-based. The hidden data remained inaudible to a human listener, confirmed by successfully replaying the file without any audible distortion.

Exercise 6 — Text Steganography

Objective: implement text-based steganography by hiding a message within the encoding of a plain text file.

Wrote a short Python script to convert a secret message to binary and encode each bit as an invisible zero-width Unicode character (zero-width space for "0", zero-width non-joiner for "1"), appended to the end of an innocuous cover sentence, then compared byte counts of the original cover file and the hidden version to demonstrate the presence of hidden data despite no visible difference. A second script decoded the zero-width characters back into the original message.

The file containing the hidden message displayed identically to the plain cover sentence when viewed with cat — no visible difference at all. Byte-count comparison showed a clear size difference: 39 bytes for the plain cover text versus 87 bytes for the version with hidden zero-width characters. The decoding script correctly recovered the original 2-character secret message ("HI") from the invisible characters.

This exercise used zero-width Unicode characters (U+200B, U+200C) as the hiding mechanism, since it is a reliable and easily reversible method to implement and verify programmatically. The key finding — text and content appearing visually identical to the human eye while differing at the byte level — is the clearest, most direct demonstration in the module of the core principle of data hiding: an observer must inspect the raw underlying data, not just the rendered output, to detect anything unusual. This method's main weakness is fragility to text processing: copying the text into many applications, or any process that strips non-printable Unicode characters, would destroy the hidden message entirely — arguably making it even more fragile than image or audio LSB steganography.

Exercise 7 — Challenges in Data Hiding Detection

Objective: investigate the challenges in steganalysis, including the effect of compression.

Re-ran StegExpose against the Week 1 test folder to confirm whether the tool/runtime compatibility issue persisted, performed a compression round-trip test on the Exercise 5 audio carrier (WAV → MP3 via LAME → back to WAV), then attempted to extract the previously embedded message from the recompressed file.

StegExpose again produced no console output, consistent with the Week 1 finding. Extraction from the recompressed audio failed three times in a row with "could not extract any data with that passphrase!", despite the correct passphrase — confirming the hidden message did not survive the MP3 compression round trip. Interestingly, file sizes for the original and recompressed WAV files were identical (137,134 bytes each), since WAV file size is determined by duration and audio format rather than the specific sample values — meaning file-size comparison, unlike the image compression test, was not a useful detection signal here.

Step-by-step guide — basic steganalysis on a suspect file:
  1. Establish a clean baseline (same source, same original size/format).
  2. Compare file size (ls -la / wc -c) — even a few KB difference can indicate embedded data.
  3. Check metadata with exiftool — rules out obvious anomalies and gives a property baseline.
  4. Attempt automated statistical analysis (e.g. StegExpose) — treat a failed run as a documented tool limitation, not proof the file is clean.
  5. Inspect the LSB plane visually against the baseline for structural irregularities.
  6. Cross-reference all signals — treat a finding as credible only when multiple independent methods point the same way.

Exercise 8 — Practical Countermeasures for Data Hiding

Objective: explore countermeasures to mitigate data-hiding risks, specifically combining encryption with steganography.

Encrypted a message using GPG with AES-256, converted a PNG cover image to JPEG and embedded the encrypted (not plaintext) file into it using Steghide, then extracted and decrypted it, confirming both layers of protection worked together correctly.

Combining encryption with steganography provides defence in depth against data hiding's core weakness: concealment alone offers no protection once an attacker successfully detects and extracts the hidden file, since Steghide's own commands are publicly documented and simple to run. With an encryption layer added, successful detection and extraction only yields ciphertext, protected by a separate passphrase the attacker does not have — meaning the two failure points (detection of the hidden file, and compromise of the encryption key) must both occur for the attacker to succeed.

Exercise 9 — Watermarking for Digital Media Protection

Objective: implement digital watermarking to indicate ownership of a media asset, and verify it can be recovered on demand.

Embedded an ownership statement (name, course code, institution, year) into a converted JPEG image using Steghide, confirmed the resulting image displayed with no visible alteration, and extracted the watermark to verify it could be recovered correctly, simulating an ownership verification check.

Extraction succeeded, recovering the exact ownership string: "OWNERSHIP: Ruqayya | CYB402 | MIVA Open University | 2026". This exercise consolidates the invisible-watermarking approach from Exercise 3, applied specifically as a copyright/ownership verification workflow: the media asset itself is unaltered in appearance, but an owner can prove authorship at any time by extracting the embedded string with the correct tool and passphrase — protecting digital media in a way a visible watermark cannot, since nothing about the image's appearance changes. As established throughout this module's compression testing, this protection is contingent on the file not being recompressed or reformatted after distribution — a limitation worth disclosing alongside any real-world use of this technique.
