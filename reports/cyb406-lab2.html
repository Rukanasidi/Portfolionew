GPG / PGP RSA & AES Digital Signatures Privacy Audit

1. Cryptographic Logic

This lab moves beyond password-based security to practice asymmetric encryption using GnuPG (via the Kleopatra front-end), and closes with a personal digital security and privacy audit covering social media settings, multi-factor authentication (MFA), and privacy-focused browser tooling.

Two distinct cryptographic algorithms were used together, each suited to a different part of the problem:

  • AES (Advanced Encryption Standard) is a symmetric-key algorithm — the same key encrypts and decrypts data. It is extremely fast on large amounts of data, which is why GPG uses it (in practice, a variant of it) to encrypt the actual file contents. Its weakness is key distribution: both parties must somehow already share the same secret key, which is impractical over an insecure channel or with someone never met in person.
  • RSA is an asymmetric (public-key) algorithm — a mathematically linked key pair, a public key that can be shared openly, and a private key that must be kept secret. RSA is computationally slower than AES, so it is impractical to encrypt an entire large file directly. Instead, GPG uses RSA to securely encrypt a randomly generated, one-time AES session key, which then encrypts the actual message or file. The recipient uses their private RSA key to decrypt that session key, then uses the recovered AES key to decrypt the file itself.

This hybrid approach — RSA for key exchange, AES for bulk data encryption — combines RSA's ability to solve the key-distribution problem with AES's speed advantage for encrypting actual content. This is exactly the workflow Kleopatra performed automatically: selecting a recipient's public certificate to "encrypt for" a file used RSA to protect the session key, while the file body itself was handled through the faster symmetric cipher.

A digital signature was also applied using the sender's private RSA key. Unlike encryption (which uses the recipient's public key), signing uses the sender's own private key to produce a signature that anyone holding the sender's public key can verify. This does not protect confidentiality — it protects authenticity and integrity, proving the message genuinely came from the claimed sender and was not altered in transit.

2. Verification Log

Two OpenPGP key pairs were generated in Kleopatra (RSA, 3,072-bit primary and encryption subkeys, 3-year validity), simulating a sender and a recipient ("peer") for the exchange:

  • Peer B Test — fingerprint: C715 803B 46A6 C92B 16A8 A0B4 9E26 BFBB 0A07 5053

A plain text file (secret_message.txt) was created, then encrypted for the peer's public key and simultaneously signed with the sender's private key using Kleopatra's Sign/Encrypt Files function, producing secret_message.txt.gpg. The recipient ("Peer B Test") then used their private key passphrase to run Decrypt/Verify Files on this encrypted file.

The result confirmed three things simultaneously: (1) decryption succeeded, meaning only the intended recipient's private key could unlock the file; (2) the digital signature was verified as valid, confirming the file genuinely originated from the claimed sender and had not been tampered with in transit; and (3) the certificate's trust chain was accepted by Kleopatra as "ultimately trusted."

On hash collisions and integrity: a cryptographic hash function takes an input of any size and produces a fixed-size digest. A digital signature works by signing the hash of a message, not the message itself, because hashing is much faster than signing the entire file with RSA. A hash collision occurs when two different inputs produce the same hash output — an event that should be computationally infeasible for a secure hash algorithm such as SHA-256. If an attacker could find a collision, they could theoretically substitute a malicious file with the same hash as the original, allowing a valid signature to be attached to forged content without detection. This is why deprecated hash functions like MD5 and SHA-1, both of which have known practical collision attacks, are no longer considered safe for digital signatures, and why modern PGP implementations default to SHA-256 or stronger.

3. Audit Reflection

A personal digital audit was carried out across two active social media accounts (Instagram and Facebook), account security (MFA), and browser privacy tooling.

Social media privacy settings

These settings have remained largely unchanged since the accounts were created approximately four years ago — itself a notable finding: privacy settings are typically configured once, during onboarding, and rarely revisited as an account's follower count, content volume, and personal risk profile grow over time. Specific exposures identified: an Instagram account left fully Public rather than Private; tag and mention approval left open to everyone with no manual review step; Facebook Reels set to Public despite ordinary posts being restricted to Friends; and the Facebook profile still discoverable through external search engines. By contrast, the phone number field on Facebook was already correctly restricted to "Only me," showing that privacy awareness was applied selectively rather than uniformly — most likely because that particular setting was noticed and consciously changed at some point, while less prominent settings were left at their platform defaults.

Multi-Factor Authentication (MFA)

MFA is already enabled on all personal and academic email accounts, using phone-based passkey authentication in combination with a registered recovery email as a fallback channel. This constitutes a layered authentication model: something known (password), something possessed (the phone/passkey), and a recovery path if the primary device is unavailable. Passkey-based authentication is also more phishing-resistant than legacy SMS or email one-time-passcodes, since it relies on cryptographic challenge-response tied to the physical device rather than a code that can be intercepted, forwarded, or socially engineered out of the account holder.

Privacy-focused browser extension

uBlock Origin Lite was installed on the primary desktop browser (Google Chrome) to reduce third-party ad and tracker exposure during normal browsing.

Behavioural vulnerabilities and overall reflection

Taken together, this audit shows an uneven security posture: strong, deliberate protections exist where the perceived stakes are obvious (email account takeover, phone number exposure), while lower-salience settings such as content visibility defaults and third-party tracking were left unmanaged for years simply because they were never revisited. This pattern — treating security as a one-time setup task rather than an ongoing practice — is one of the most common behavioural vulnerabilities in personal digital security, and is precisely the gap that a periodic self-audit, such as this lab exercise, is designed to close. Following this audit, specific low-effort corrections are now planned: switching Instagram to Private, requiring manual tag approval on both platforms, and disabling external search-engine indexing on Facebook.
